How it's built:the published method, installed as taught

Drop an agent into a repo and it needs three answers. What am I doing? How is it done here? And what should I not load — the context window is finite, and every irrelevant file dilutes the relevant ones. Teams fail this both ways: one giant file the agent drowns in halfway through the task, or thirty scattered docs it never opens. The task comes from your engineer. The other two answers have to live in the repo. That is what these layers are.

Layer 1 · CLAUDE.md

The map

Always loaded, every session: every folder, every naming rule, every placement rule. The agent's GPS. It ends the grep, grep, ls, grep of a lost agent rediscovering where payments lives.

Layer 2 · CONTEXT.md

The router

What's your task? Go here, and you'll also need X. A migration task loads the migration contract and the ADR that says why Kafka and not a cron, never the whole monorepo.

Layer 3 · workspace/CONTEXT.md

The workspace contracts

A self-contained scope per workspace: what to load, inputs, outputs, and the conventions your reviewers repeat in every PR, "we don't mock the payment gateway". An agent drops in, reads its contract, does the work, exits.

The three truthsnobody opens with

You should hear these from us, before you buy anything from anyone.

Truth 01
A readable file is a copyable file

File systems have no "read but don't take". Secrets never live in this structure, only references to your secret manager. Design boundary, not a footnote.

Truth 02
The structure declares; git and your OS enforce

Anyone telling you a context method IS your security is selling a story. The fences live one layer down: protected branches, CODEOWNERS, read-only distribution. We set them up with you.

Truth 03
Human gates don't scale by themselves

Review gates are the trust feature and the first bottleneck. Every gate ships with an owner, a queue and an SLA, or it becomes a gate people walk around.
